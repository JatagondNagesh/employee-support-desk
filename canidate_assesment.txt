Employee policy and reimbursement triage
Your task
Build a local application for an employee support desk serving multiple organizations. It must answer policy questions and turn submitted reimbursement requests into a review report. The supplied information includes different roles, changing policies, inconsistent records, and documents that cannot always be processed reliably.
Use a Spring Boot public API backed by a Python service. Spring Boot owns caller context, request validation, and the public response. Python handles document extraction, policy retrieval, and answer generation. This document contains the complete starting dataset; no starter repository or separate data package is provided.
Required capabilities
•
Answer policy questions using relevant, approved evidence for the caller's tenant, role, and requested date. Return a supported answer, insufficient evidence, or an unresolved policy conflict with the citation contract on page 2.
•
Accept a small batch of UTF-8 TXT and text-based PDF requests. Extract the requested benefit, stated amount, currency, and reference, with source quotations for supported values. Keep missing or ambiguous values visible rather than guessing.
•
For each request, report what the applicable policy says about the requested benefit and what needs human review. An annual policy limit does not establish remaining balance, expense eligibility, or a payable amount. No claims history is supplied.
•
Keep a result for every submitted item, including exact duplicates and failed items. One item's failure must not prevent independent items from being processed.
•
Treat submitted text, policy passages, and model output as untrusted data. They cannot change caller identity, access rules, or application behavior. Ineligible policy passages must not reach generation or the response.
•
Keep policy records separate from application logic. The same rules must apply when records are reordered, duplicated, added, or changed within the supplied data contract.
Every submitted request requires human review. The application must not approve claims, initiate payments, or send messages to employees. Submitted requests are not policy sources.
Effort and boundaries
Prioritize a working end-to-end path and meaningful tests. AI coding tools are allowed; you remain responsible for explaining the implementation.

Public API contract
Expose both endpoints through Spring Boot. Require X-Caller-Id from page 3 and a valid as_of date
in YYYY-MM-DD format. Reject missing or unknown callers. For this exercise only, the header
simulates authenticated identity; tenant and role come from the lookup, never from document or
request-body claims.
Policy questions
POST /answer Content-Type: application/json
X-Caller-Id: atlas-employee-01
{"question":"What is my annual certification reimbursement limit?",
"as_of":"2026-09-21"}
question must be a non-empty string. Return HTTP 200 with {status, answer, citations} for a business
outcome. Each citation has chunk_id (the policy ID) and quote (verbatim source text).
status answer citations
ANSWERED Supported answer string Supporting eligible quotations
INSUFFICIENT_EVIDENCE null Empty array
CONFLICT null Eligible quotations showing disagreement
Batch intake
POST /batches is synchronous multipart/form-data. Send one metadata JSON part and repeated files
parts. Each uploaded filename must match one manifest entry; document_id and filename must be
unique within the manifest. Use one caller and one as_of date for the entire batch.
{“batch_id”: “demo-01”, "as_of": "2026-09-21", "documents": [{"document_id": "request-01",
"filename": "request-01.txt"}]}
Return HTTP 200 after processing with batch_id, summary {total, completed, failed}, and results in
manifest order. Return one result per entry, using the fields below. Choose and document the nested
JSON shapes.

The /answer response shape for the requested benefit; null if processing failed or the

Always true; an array of review reasons, including unresolved input information and relevant

Invalid metadata, duplicate manifest identifiers, or missing/extra file parts fail the whole batch with
non-2xx. An empty or unreadable file, or an item-level dependency failure, produces FAILED for that
item; other items continue. /answer dependency failures require non-2xx. Timeouts and malformed
model output are failures, not insufficient evidence. Set bounded timeouts, allow at most one model
generation attempt per question or item, and disable automatic retries.

Evidence boundaries
Use relevant evidence, not merely a matching keyword or the first retrieved passage. No precedence
rule is supplied for contradictory, simultaneously applicable policies. Do not invent one. General world
knowledge and submitted request text cannot fill gaps in the policy corpus.
For batch intake, identify the benefit and report the available policy terms, without deciding whether
that particular request is payable. Ambiguous input fields and conflicting policies are different
conditions and must remain distinguishable. Explain unsupported conclusions through the review
reasons.
